# Cloudflare Worker: диагностика Mischenko Edu

Исходник: `worker.js`. Миграции D1: `schema.sql`, затем для существующей базы — `migrations/0002_telegram_outbox.sql`, `migrations/0003_curriculum_and_consent.sql` `migrations/0004_curriculum_level.sql` и `migrations/0005_curriculum_year.sql` (каждую ровно один раз).

## Текущее состояние
Этот код подготовлен, но не развернут в Cloudflare автоматически. Для центрального архива необходимо подключить D1 и заменить код существующего Worker этим исходником.

## Настройка
1. В Cloudflare Workers & Pages откройте Worker `mischenko-edu-diagnostics`.
2. Создайте D1 database, например `mischenko-edu-diagnostics`.
3. Для новой базы выполните актуальный SQL из `schema.sql`. Для уже существующей базы проверьте историю миграций и примените недостающие `0002_telegram_outbox.sql`, `0003_curriculum_and_consent.sql` `0004_curriculum_level.sql` и `0005_curriculum_year.sql` ровно по одному разу.
4. В Worker → Settings → Bindings добавьте D1 binding с variable name `DB` и выберите созданную базу.
5. В Variables and Secrets проверьте секреты `BOT_TOKEN` и `OWNER_CHAT_ID`. Не помещайте их в HTML или GitHub.
6. Добавьте Secret `ADMIN_TOKEN` — длинный случайный пароль для просмотра архива.
7. Замените код Worker содержимым `worker.js` и Deploy.
8. В Worker → Settings → Triggers добавьте Cron Trigger `0 3 * * *` (ежедневно в 03:00 UTC) для очистки записей старше срока хранения. Переменная `DATA_RETENTION_DAYS` необязательна; допустимо 30–365, по умолчанию 180.
9. Проверьте GET `/`: ответ должен содержать `"database":true`.
10. Проведите интеграционный тест на синтетической записи с `telegramConsent: false`, проверьте её появление в архиве и удаление через кнопку архива. Не используйте реальные данные ученика и не отправляйте тестовое сообщение в рабочий Telegram.
11. Только после успешной проверки откройте `edu/diagnostika.html`: установите `REMOTE_SAVE_ENABLED=true` и уберите `hidden` у `#consent-panel`. Затем запустите CI и проверьте сценарий на тестовой записи.

## API
- `POST /diagnostics` — проверяет согласие на архив, имя, класс, направление, учебную программу и ровно 15 ответов; сохраняет попытку в D1. Telegram отправляется только при отдельном `telegramConsent: true`.
- `GET /admin/attempts?limit=50` — возвращает архив только при заголовке `Authorization: Bearer ADMIN_TOKEN`.
- `DELETE /admin/attempts/{attemptId}` — удаляет одну попытку только при заголовке `Authorization: Bearer ADMIN_TOKEN`.

Telegram — необязательное уведомление, D1 — постоянный архив. Выбор программы, её уровень, название и уточнение сохраняются отдельно для каждой попытки. Повторная отправка с тем же `attemptId` не создаёт вторую запись. Состояние Telegram-хука хранится в D1: при временной ошибке статус возвращается в `pending`, и клиент может повторить POST с тем же `attemptId`. Успешно отправленное уведомление повторно не отправляется; зависший статус `sending` можно перехватить после двух минут.

## Важно
- В этой версии endpoint архива — технический API, а не готовая публичная админ-панель.
- Не добавляйте ADMIN_TOKEN в публичный HTML, репозиторий или клиентский JavaScript.
- Перед публичным запуском проверьте юридическую применимость уведомления, статус оператора данных, регион хранения и условия внешних сервисов. Технический срок хранения по умолчанию — 180 дней, но автоматическая очистка работает только после настройки Cron Trigger.
- Не включайте реальную отправку результатов до успешной проверки D1, Telegram opt-in, архива, DELETE и Cron на тестовой записи.
- Выбор программы пока записывается в архив; текущие общие банки не становятся автоматически соответствующими российской или белорусской программе. Для этого требуются отдельные банки и проверка по актуальным учебным программам.
- Worker возвращает `saved:true` отдельно от `telegramSent`: сохранение в базе и доставка уведомления — разные операции.
- Для существующей D1 базы не запускайте повторно миграцию 0002: SQLite не допускает повторного добавления тех же колонок.
